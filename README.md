# Threadsタロット3択ポスト自動投稿システム（GAS + スプレッドシート）

投稿キューシートに書いた質問文から、タロットカードを3枚抽選し、Claude APIでリプライ本文①②③を
生成。承認後にThreads APIへ、画像3枚（カルーセル）付きの本体投稿＋①②③のリプライ3件を
自動投稿するシステムです。

## 全体フロー

1. **生成バッチ**（毎日12:00・`dailyGenerationBatch`）
   投稿キューシートの未処理行（質問のみ入っていて投稿予定日時が未設定の行）を最大10件取り出し、
   「翌日」の10スロット（7:00〜24:00, 約113分間隔）に割り当てる。各行について、
   - `TarotService.prepareDraw()`でカードを3枚抽選（カード名重複なし）し、対応する画像を
     タロット画像フォルダから解決
   - `ClaudeService.generateTarotCaptions()`で質問文＋カード情報からリプライ本文①②③を生成
   - 固定文言＋質問文で本体投稿の本文を組み立て
   これらをシートに書き戻す。承認ステータスは「未確認」になる。
2. **人による確認**
   スプレッドシート上で本文・カード・画像を確認し、承認ステータスを `OK` または `NG` に変更する。
   `NG`にした行は生成ステータスを「未生成」に戻すと次回バッチで再生成される。
3. **投稿巡回**（15分おき・7:00〜24:00・`postingCycle`）
   投稿予定日時を過ぎていて承認ステータスが`OK`の行を検出し、
   ① 画像3枚＋固定文言＋質問文で本体投稿 → ② その投稿に対して①②③のリプライを順番に投稿、の順で実行する。
   本体投稿が成功した時点で投稿ステータスを「本文投稿済み(リプライ未完了)」にして即座に保存するため、
   リプライの途中で失敗しても、本体の再投稿やリプライの重複投稿を起こさず次回サイクルで再開できる。
   予定日時を過ぎても未承認のままの行は「スキップ(未承認)」として記録し、投稿しない。
4. **トークン自動更新**（毎日3:00・`tokenRefreshCheck`）
   Threadsの長期アクセストークン（60日有効）の残り期限が7日以内になったら自動更新する。

## 投稿キューシートの列構成

| 列 | 項目 | 内容 |
|---|---|---|
| A | No | 行ID |
| B | 質問 | 手動入力する質問文 |
| C〜E | 画像1〜3 | 生成バッチが自動解決するDriveファイルID（手動入力不要） |
| F | 投稿予定日時 | 生成バッチが自動算出 |
| G | 投稿本文(本体) | 固定文言＋質問文（生成バッチが自動組み立て） |
| H〜J | リプライ本文①〜③ | 本体投稿へのリプライとして投稿する本文（投稿種別を問わない汎用列。タロット投稿ではClaudeが生成した本文が自動で入る。それ以外の投稿では運営が手動入力する） |
| K | 生成ステータス | 未生成 / 生成済み / 生成エラー |
| L | 承認ステータス | 未確認 / OK / NG（人が確認して設定） |
| M | 投稿ステータス | 未投稿 / 本文投稿済み(リプライ未完了) / 投稿済み / スキップ(未承認) / 投稿エラー |
| N | 実投稿日時 | 本体投稿の実績日時 |
| O | Threads投稿ID(本体) | 本体投稿のID |
| P | エラーメッセージ | 直近のエラー詳細 |
| Q | 最終更新日時 | 自動更新 |
| R〜T | カード①〜③ | 抽選されたカード名・向き（例: `節制(正)`、レビュー用の表示） |
| U〜W | リプライ①〜③投稿ID | 各リプライ投稿のThreads投稿ID（再実行時の重複投稿防止・進捗管理に使用） |

リプライ本文①〜③は空欄でも構わない。`PostingService`は本体投稿の成功後、①→②→③の順に中身をチェックし、
**空でないものだけ**順番にリプライとして投稿する（空欄はエラーにせずスキップする）。

## タロットカード抽選について

- カード意味は投稿キューと同じスプレッドシート内の「カード意味」シート
  （列構成: A=カード名, B=向き, C=意味, D=キー(未使用)）で管理する。
- 抽選はカード名でグルーピングしてから重複なく3件選ぶため、同じカードの正逆違いが重複することはない。
- 画像は`ALLOWED_DRIVE_FOLDER_ID`のフォルダから、`カード名_正逆_①②③.png`
  （例: `節制_正_①.png`）というファイル名で検索して取得する。カード名・向きの表記は
  カード意味シートの表記とファイル名が完全一致している必要がある。

## 開運日カレンダーについて

- 投稿キューと同じスプレッドシート内の「開運日カレンダー」シート
  （列構成: A=日付, B=曜日, C=開運日(複数ある場合はカンマ区切り、例: `大安,一粒万倍日`)）を参照する。
- `KaiunService.findLuckyDaysForDate(date)`で指定した日付に該当する開運日名の配列を取得できる
  （該当なしの場合は空配列）。A列は文字列(`yyyy-MM-dd`形式)・Date型のどちらで入力されていても
  正しく比較できるようになっている。
- 現時点ではこの判定機能のみを提供しており、生成バッチ（`SchedulerService`）から実際に
  「開運」タイプの投稿を振り分けたり、該当日がない場合に他のタイプへ差し替えたりする処理は
  まだ組み込んでいない（今後実装予定）。

## 情弱ポスト（拡散狙いのフックポスト）について

- `ClaudeService.generateJoujakuCaption()`で本文を1件生成する（引数なし）。画像・リプライは無く、
  本文のみのテキスト投稿（`ThreadsService.publishPost`の画像0枚パス＝TEXTコンテナ）を想定している。
- 元のプロンプトは5パターンを一度に出力する仕様だったが、自動化のため「フックの種類・メッセージの
  方向性をランダムに1組だけ選び、1パターンのみ出力する」よう`buildJoujakuPrompt_`内で調整している
  （フック・方向性の抽選自体はコード側では行わず、プロンプトの指示に従ってClaude側で行わせる）。
- 「有効期間」は実際の日付を渡さず、プロンプトの指示で「〇日〜〇日」「今日中」などのプレースホルダー
  表現のまま出力させる（実日付への書き換えは運営が投稿前チェック時に手動で行う想定）。
- 各パターン末尾に付く「（フック種類×メッセージの方向性）」のようなメモ書きは出力させない指示を
  入れているが、保険として`stripTrailingHookMemo_`で応答末尾のその形式のかっこ書きを機械的に除去する。
- 現時点では`SchedulerService`からの呼び出し（投稿タイプ振り分けへの組み込み）は行っていない。

## セットアップ手順

### 1. スプレッドシートとスクリプトの用意

1. 新規Googleスプレッドシートを作成する。
2. 「拡張機能」→「Apps Script」を開き、このスクリプトを紐づける（コンテナバインド型）。
3. `src/` 配下の各ファイルをApps Scriptエディタにコピーする（`.gs`拡張子で保存、`appsscript.json`は「プロジェクトの設定」から表示・編集）。
   `clasp` を使う場合は `clasp push`（`rootDir: src`）でも可。

### 2. スクリプトプロパティの設定

「プロジェクトの設定」→「スクリプト プロパティ」で以下を設定する。

| キー | 内容 |
|---|---|
| `CLAUDE_API_KEY` | Claude APIキー |
| `CLAUDE_MODEL` | （任意）モデルID。未設定時は `claude-sonnet-5` |
| `THREADS_ACCESS_TOKEN` | Threads長期アクセストークン |
| `THREADS_USER_ID` | Threadsのユーザー（アプリ）ID |
| `THREADS_TOKEN_EXPIRES_AT` | トークン取得時の有効期限（ISO8601、例: `2026-09-25T00:00:00Z`） |
| `ALLOWED_DRIVE_FOLDER_ID` | タロットカード画像を置くDriveフォルダID |

### 3. 画像フォルダの共有設定

- `ALLOWED_DRIVE_FOLDER_ID`のフォルダに、カードごとの画像（`カード名_正逆_①②③.png`）を配置し、
  フォルダを「リンクを知っている全員」に共有しておく（Threads側のサーバーが画像を取得できるようにするため）。
- 「カード意味」「開運日カレンダー」シートは、このスプレッドシート内に用意しておく
  （別スプレッドシートの共有設定は不要）。

### 4. 初期化

Apps Scriptエディタで以下を一度だけ手動実行する。

1. `initializeSpreadsheet` — 5つのシート（投稿キュー/設定/トークン状態/実行ログ/開運日カレンダー）と見出し行を作成
   （「カード意味」シートは既存のデータをそのまま使うため、この処理では作成しない）
2. `installTriggers` — 生成バッチ・投稿巡回・トークン更新の3トリガーを作成

初回実行時、Drive/スプレッドシート/UrlFetchApp等の権限承認が求められるので許可する。

### 5. 運用

1. 投稿キューシートの「質問」列に質問文を入力しておく（画像・カード列は自動で埋まるため入力不要）。
2. 毎日12:00に翌日分のカード抽選・本文生成が自動で行われる。
3. 生成された本体投稿文・カード・リプライ本文①②③を確認し、承認ステータスを`OK`（またはNG）に変更する。
4. 承認済みの行は、投稿予定日時になると本体投稿→リプライ①②③の順で自動投稿される。

## 画像URLについて（設計上の注意）

当初は「Apps ScriptのWebアプリ(doGet)で許可フォルダのファイルIDのみ受け付ける画像プロキシ」を
実装していましたが、**Google Apps ScriptのWebアプリはTextOutput/HtmlOutputしか返却できず、
画像のようなバイナリを直接配信することができない**ことが実機検証で判明したため（`doGet`から
Blobを直接returnすると「返された値はサポートされている戻り値の型ではありませんでした」という
エラーになる）、この方式は廃止しました。

代わりに、`DriveService.getPublicImageUrl`でDriveファイルIDから
`https://lh3.googleusercontent.com/d/<ファイルID>` 形式の直リンクを組み立てて、
Threads APIの`image_url`にそのまま渡す方式にしています。「許可フォルダ内の画像のみ使う」という
制限は、取得時点でのゲートではなく、**投稿本文の生成時（SchedulerService、タロット画像フォルダから
しか検索しないため自動的に満たされる）と投稿直前（PostingService）の2箇所で
`DriveService.assertImagesAllowed`により事前検証し、フォルダ外のファイルIDが指定されていれば
処理を止めてエラーとして記録する**ことで実現しています。

対象ファイルはDrive上で「リンクを知っている人」に共有しておく必要があります。

## 注意事項

- Threads APIのエンドポイント・パラメータ仕様は変更される可能性があるため、実装後に
  実際のレスポンスを確認しながら調整してください（特にリプライ投稿時の`reply_to_id`パラメータ）。
