# Threads自動投稿システム（GAS + スプレッドシート）

タロット3択・情弱ポスト・開運ポスト・HSPあるあるポスト・数秘術ポストの5種類の投稿を、
投稿タイプ別シートで「生成 → 内容確認 → 承認(OK)」し、承認済みの投稿だけを投稿キューシートへ
自動転記してスケジュール投稿するシステムです。

## 全体フロー

1. **生成**（手動実行）
   投稿タイプごとに用意した専用シート（タロットポスト／情弱ポスト／開運ポスト／
   HSPあるあるポスト／数秘術ポスト）に対し、`GenerationService`の対応する関数を手動実行して
   本文を生成する。生成方法はタイプによって異なる（後述）。生成された行の承認ステータスは
   「未承認」になる。
2. **人による確認・承認**
   各シート上で本文（タロットは画像・カードも）を確認し、承認ステータスを`OK`または`NG`に変更する。
3. **投稿キューへの自動転記**（1時間おき・`transferCycle`）
   1日10枠の固定スケジュール（時刻・投稿タイプの並び順とも固定）に従って、承認済みの行を
   該当する枠へコピーする。翌日が開運日カレンダーに載っているかどうかで、開運ポストを含む
   パターンと含まないパターン（開運の枠がHSPあるあるに置き換わる）を自動で切り替える。
   コピー元行は転記ステータスを「転記済み」に更新する（重複防止）。ある枠に対応する承認済み行が
   まだ無い場合は無理に埋め合わせず、その枠は空いたまま次回サイクルに持ち越す。詳細は
   [投稿キューへの自動転記について](#投稿キューへの自動転記について)を参照。
4. **投稿巡回**（15分おき・7:00〜24:00・`postingCycle`）
   投稿予定日時を過ぎている行を検出し、① 画像（あれば）＋本文で本体投稿 → ② その投稿に対して
   リプライ本文①②③（あれば）を順番に投稿、の順で実行する。投稿キューシートに来る時点で
   既に承認済みのため、ここでは承認確認を行わない。本体投稿が成功した時点で投稿ステータスを
   「本文投稿済み(リプライ未完了)」にして即座に保存するため、リプライの途中で失敗しても、
   本体の再投稿や投稿済みリプライの重複投稿を起こさず次回サイクルで再開できる。
5. **トークン自動更新**（毎日3:00・`tokenRefreshCheck`）
   Threadsの長期アクセストークン（60日有効）の残り期限が7日以内になったら自動更新する。
6. **投稿インサイトの集計**（毎朝8:00・`insightsCollection`）
   投稿ステータスが「投稿済み」または「本文投稿済み(リプライ未完了)」で、実投稿日の2日後以降になった
   行から、いいね数・返信数・リポスト数・表示回数を1回だけ取得して記録する。詳細は
   [投稿インサイトの集計について](#投稿インサイトの集計について)を参照。

## シート構成

### 投稿キューシート（スケジュール管理・投稿実行専用。生成は行わない）

| 列 | 項目 | 内容 |
|---|---|---|
| A | No | 行ID |
| B | 投稿タイプ | タロット／情弱／開運／HSPあるある／数秘術（表示・監査用） |
| C | 投稿予定日時 | 転記時にTransferServiceが自動算出 |
| D〜F | 画像1〜3 | タロットのみ使用（Driveファイル ID）。他タイプは空欄 |
| G | 投稿本文 | 転記時にコピーされる本体投稿文 |
| H〜J | リプライ本文①〜③ | 転記時にコピーされる。空欄の分はリプライ投稿がスキップされる |
| K〜M | リプライ①〜③投稿ID | 各リプライ投稿のThreads投稿ID（再実行時の重複投稿防止・進捗管理に使用） |
| N | 投稿ステータス | 未投稿 / 本文投稿済み(リプライ未完了) / 投稿済み / 投稿エラー |
| O | 実投稿日時 | 本体投稿の実績日時 |
| P | Threads投稿ID | 本体投稿のID |
| Q | エラーメッセージ | 直近のエラー詳細（投稿インサイト集計の失敗時もここに記録される） |
| R | 最終更新日時 | 自動更新 |
| S | いいね数 | 投稿から2日後の朝にThreads Insightsから取得 |
| T | 返信数 | 同上 |
| U | リポスト数 | 同上 |
| V | 表示回数 | 同上（views） |
| W | 集計ステータス | 未集計 / 集計済み（1度取得したら以降は更新しない） |

### 投稿タイプ別シート（共通列）

5つのシート（タロットポスト／情弱ポスト／開運ポスト／HSPあるあるポスト／数秘術ポスト）は、
以下の列を共通で持つ。

| 項目 | 内容 |
|---|---|
| 投稿本文 | 生成された本体投稿文 |
| リプライ本文①〜③ | 本体投稿へのリプライ本文（タロットは自動生成。他タイプは運営が任意で手動入力してよい） |
| 承認ステータス | 未承認 / OK / NG（NGの行は転記対象から除外される） |
| 転記ステータス | 未転記 / 転記済み（転記時に自動更新） |
| 生成日時 | 生成バッチ実行時に自動記録（記録用。転記順の判定には使わない） |

### 投稿タイプ別シート（タイプごとの追加列）

| シート | 追加列 | 内容 |
|---|---|---|
| タロットポスト | 質問、画像1〜3、カード①〜③ | 質問は手動入力。画像・カードは生成時に自動で埋まる |
| 開運ポスト | 日付、開運日 | ともに生成時に自動で埋まる（開運日カレンダーを参照） |
| 数秘術ポスト | テーマ、グループ | ともに手動入力（グループは1〜6 または 7〜9・11・22・33）。自動生成は行わず、投稿本文も含めて運営が手動で入力する |
| 情弱ポスト／HSPあるあるポスト | なし | 共通列のみ |

## 生成方法（タイプごとに異なる）

- **タロット**（`generateTarotBatch`）: タロットポストシートの「質問が入っていて投稿本文が空」の
  行を対象に、カード抽選・画像解決・リプライ本文生成・本体投稿文の組み立てをまとめて行う。
  あらかじめ「質問」列に入力しておいた分だけ処理される。
- **数秘術**: 自動生成は行わない方針のため専用の生成関数は無い。テーマ・グループを参考にしつつ、
  投稿本文・リプライ本文①〜③を運営が直接シートに入力し、承認ステータスを`OK`にする。
- **情弱／HSPあるある**（`generateJoujakuBatch` / `generateHspAlarmBatch`）: 手動実行1回につき、
  対応するClaude生成関数を10回呼び出し、生成結果をシートに10件追加する。
- **開運**（`generateKaiunBatch()`）: 「開運日カレンダー」シートに書かれている行を上から順に確認し、
  まだ生成していない日付を最大`KAIUN_BATCH_MAX_`（31）件まで生成する。このシートには運用側が
  「投稿したい開運日」だけを厳選して貼り付ける運用のため、任意の日付範囲を1日ずつ走査してスキップする
  処理は行わない（該当日以外の空白の日付行は存在しない前提）。

タロットは投稿ステータス列を持たない代わりに投稿本文が空かどうかで生成要否を判定するため、
生成に失敗した行は投稿本文が空のまま残り、次回`generateTarotBatch`を実行すれば自動的に
再試行される。生成タイプ別シートにはエラーメッセージ列を設けていないため、失敗の詳細は
実行ログシートおよびApps Scriptの実行トランスクリプトで確認する。

## 投稿キューへの自動転記について

`TransferService.runTransferCycle()`が1時間おきに実行され、「翌日」ぶんについて次の処理を行う。

### 1日10枠の固定スケジュール

投稿の時刻・タイプの並び順は、以下の2パターンに固定されている（`Config.gs`）。

- `Config.SLOT_MINUTES`：1日10枠の固定時刻。7:00〜21:24を96分間隔で10等分
  （7:00, 8:36, 10:12, 11:48, 13:24, 15:00, 16:36, 18:12, 19:48, 21:24）。
- `Config.DAILY_PATTERN_WITH_KAIUN`（開運ポストがある日）：
  開運 / タロット / 情弱 / 数秘術 / タロット / 情弱 / タロット / 情弱 / HSPあるある / 情弱
  （タロット3・情弱4・開運1・HSPあるある1・数秘術1 = 計10件）
- `Config.DAILY_PATTERN_WITHOUT_KAIUN`（開運ポストがない日）：
  開運の枠がHSPあるあるに置き換わる以外は同じ並び。
  HSPあるある / タロット / 情弱 / 数秘術 / タロット / 情弱 / タロット / 情弱 / HSPあるある / 情弱
  （タロット3・情弱4・HSPあるある2・数秘術1 = 計10件）

どちらのパターンを使うかは、`KaiunService.listEntries()`で**開運日カレンダーシートに翌日の日付が
存在するかどうか**だけで決まる（開運ポスト自体がまだ承認されているかどうかは見ない）。
`Config.POST_TYPES`の各タイプには固定のクォータ（1日あたりの必要件数）は持たせておらず、
上記パターン配列に何回登場するかで実質的なクォータが決まる。

### 転記の進め方

1. 投稿キューシートに既に存在する「翌日」の行をタイプ別に集計する（`countByType`）。
2. 選んだパターンを先頭の枠（7:00）から順に見ていく。各タイプについて「パターン内で何回目の
   登場か」を数え、その回数が`countByType`の件数未満なら「前回までのサイクルで転記済みの枠」
   とみなしてスキップする（スロットの時刻同士を直接比較する必要はない）。
3. まだ埋まっていない枠に来たら、そのタイプの承認済み・未転記の候補から未使用の1件を取り出し、
   その枠の固定時刻で投稿キューへ追加する（コピー元行の転記ステータスは「転記済み」に更新）。
   候補の選び方はタイプによって異なる。
   - **タロット・情弱・HSPあるあるポスト・数秘術**：そのタイプのシートを上から順に見て
     「承認ステータス=OK かつ 転記ステータス=未転記」の行を使う（生成日時列は転記順の判定には
     使わない）。
   - **開運ポストのみ例外**：シート上の並び順は使わず、`getApprovedUntransferredKaiunRowForDate_`が
     「投稿予定日（翌日）と開運ポストシートの日付列が一致する行」を探す。開運ポストは日付ごとに
     書かれた専用の内容のため。一致する行が無い、またはあっても未承認・転記済みの場合はその日は
     開運ポストなしとする。
4. 候補が尽きている枠は今回は埋めず、次回サイクルに持ち越す（他タイプで穴埋めしない）。

開運日カレンダーに翌日の日付が載っているのに、その開運ポストの承認が間に合わなかった場合、
開運の枠（7:00）だけが空いたままになり、HSPあるあるなど他タイプへの振替は起きない
（他8枠の内訳はパターンA通りのまま）。

何度実行しても安全（冪等）：実行のたびに「パターン内の何回目の登場が転記済みか」を数え直すため、
同じ行が二重に転記されることはない。

## 投稿インサイトの集計について

`InsightsService.runInsightsCollection()`が毎朝8:00に実行され、対象行のいいね数・返信数・
リポスト数・表示回数をThreads APIから取得して記録する。

- 対象行の条件:
  - 投稿ステータス = 投稿済み または 本文投稿済み(リプライ未完了)（本体さえ投稿されていれば
    インサイトは取得できるため、リプライが未完了というだけで除外しない）
  - 実投稿日時の「日付」+2日 ≤ 今日の日付（例: 7/1に投稿した行は7/3の朝から対象になる。
    時刻は無視して暦日で判定するため、投稿が23時台になっても2日後の朝には確実に拾われる）
  - 集計ステータス ≠ 集計済み
- `ThreadsService.getPostInsights(mediaId)`が`GET /{mediaId}/insights?metric=likes,replies,reposts,views`
  を呼び出し、結果を`{likes, replies, reposts, views}`に整形して返す。
- 取得に成功した行は、いいね数〜表示回数を書き込み、集計ステータスを「集計済み」に更新する
  （以降はこの行を二度と更新しない、1回きりの集計）。
- 取得に失敗した行は、既存の「エラーメッセージ」列に詳細を記録するだけで集計ステータスは
  更新しない。専用のエラー列は設けていないため、投稿失敗時のエラーメッセージと共用する形になる
  （集計対象になる行は投稿済みのはずなので、通常はエラーメッセージが空の状態から始まる）。
  集計ステータスが未集計のままなので、翌朝の巡回で自動的に再試行される。

**権限に関する注意**: インサイト取得には`threads_manage_insights`権限が必要。既存の投稿・リプライ用
スコープ（`threads_content_publish`など）とは別物なので、`THREADS_ACCESS_TOKEN`を発行・認可する際に
このスコープが含まれているか確認すること。含まれていない場合、`TokenService`によるリフレッシュだけでは
解決せず、認可のやり直し（トークン再発行）が必要になる可能性がある。

## セットアップ手順

### 1. スプレッドシートとスクリプトの用意

1. 新規Googleスプレッドシートを作成する。
2. 「拡張機能」→「Apps Script」を開き、このスクリプトを紐づける（コンテナバインド型）。
3. `src/` 配下の各ファイルをApps Scriptエディタにコピーする（`.gs`拡張子で保存、`appsscript.json`は「プロジェクトの設定」から表示・編集）。
   `clasp` を使う場合は `clasp push`（`rootDir: src`）でも可。

### 2. スクリプトプロパティの設定

「プロジェクトの設定」→「スクリプト プロパティ」で以下を設定する。

| キー | 内容 |
|---|---|
| `CLAUDE_API_KEY` | Claude APIキー |
| `CLAUDE_MODEL` | （任意）モデルID。未設定時は `claude-sonnet-5` |
| `THREADS_ACCESS_TOKEN` | Threads長期アクセストークン |
| `THREADS_USER_ID` | Threadsのユーザー（アプリ）ID |
| `THREADS_TOKEN_EXPIRES_AT` | トークン取得時の有効期限（ISO8601、例: `2026-09-25T00:00:00Z`） |
| `ALLOWED_DRIVE_FOLDER_ID` | タロットカード画像を置くDriveフォルダID |

### 3. 画像フォルダの共有設定

- `ALLOWED_DRIVE_FOLDER_ID`のフォルダに、カードごとの画像（`カード名_正逆_①②③.png`）を配置し、
  フォルダを「リンクを知っている全員」に共有しておく（Threads側のサーバーが画像を取得できるようにするため）。
- 「カード意味」「開運日カレンダー」シートは、このスプレッドシート内に用意しておく。

### 4. 初期化

Apps Scriptエディタで`initializeSpreadsheet`を一度だけ手動実行する。以下のシートと見出し行が
作成される（「カード意味」シートは既存のデータをそのまま使うため対象外）。

- 投稿キュー／設定／トークン状態／実行ログ／開運日カレンダー
- タロットポスト／情弱ポスト／開運ポスト／HSPあるあるポスト／数秘術ポスト

続けて`installTriggers`を実行し、転記・投稿巡回・トークン更新の3トリガーを作成する。

初回実行時、Drive/スプレッドシート/UrlFetchApp等の権限承認が求められるので許可する。

### 5. 運用

1. タロットポストシートに「質問」を入力しておく。開運・情弱・HSPあるあるは入力不要
   （開運日カレンダー参照 or まとめて自動生成）。数秘術ポストシートには「テーマ」「グループ」を
   参考情報として入力しつつ、投稿本文・リプライ本文①〜③は運営が直接入力する。
2. タロット・情弱・HSPあるある・開運は、`GenerationService`の対応する関数
   （`generateTarotBatch`など）を手動実行して本文を生成する（数秘術は対象外）。
3. 各シート上で内容を確認し、承認ステータスを`OK`（またはNG）に変更する。
4. 1時間おきの`transferCycle`が、承認済みの行を投稿キューへ自動転記する。
5. 投稿キューに転記された行は、投稿予定日時になると自動投稿される。

## タロットカード抽選について

- カード意味は投稿キューと同じスプレッドシート内の「カード意味」シート
  （列構成: A=カード名, B=向き, C=意味, D=キー(未使用)）で管理する。
- 抽選はカード名でグルーピングしてから重複なく3件選ぶため、同じカードの正逆違いが重複することはない。
- 画像は`ALLOWED_DRIVE_FOLDER_ID`のフォルダから、`カード名_正逆_①②③.png`
  （例: `節制_正_①.png`）というファイル名で検索して取得する。カード名・向きの表記は
  カード意味シートの表記とファイル名が完全一致している必要がある。

## 開運日カレンダーについて

- 投稿キューと同じスプレッドシート内の「開運日カレンダー」シート
  （列構成: A=日付, B=曜日, C=開運日(複数ある場合はカンマ区切り、例: `大安,一粒万倍日`)）を参照する。
  運用側が「投稿したい開運日」だけを厳選して貼り付ける想定で、該当日以外の空白の日付行は無い。
- `KaiunService.listEntries()`でシートの2行目以降を上から順に`{date, luckyDays}`の配列として
  丸ごと読み込める（日付が空の行は無視する）。A列は文字列(`yyyy-MM-dd`形式)・Date型のどちらで
  入力されていても、`isSameDate_`で正しく比較できるようになっている。
- `GenerationService.generateKaiunBatch`が、開運ポストシートへの一括生成時にこれを使う。
  カレンダーシートの行を上から順に確認し、開運ポストシートにまだ存在しない日付だけを対象にする
  （既存の生成済み判定ロジックをそのまま流用）。

## バズ構文シートについて

- 投稿キューと同じスプレッドシート内の「バズ構文」シート（列構成: A=No, B=バズ構文）を参照する。
  運営がこのシートに随時バズ構文を追加・削除して管理する運用。
- 情弱ポスト・HSPあるあるポスト・開運ポストの3タイプすべてで、生成のたびに
  `BuzzwordService.pickRandom()`で**コード側で1件ランダム抽選**し、「今回使うバズ構文」として
  プロンプトに明記した上で、AIに使い方を指示する。
  以前は各プロンプト内にバズワードの固定リストを直書きし、AIがその中から自分で1つ選ぶ形式
  だったが、これは他の要素（テーマ・構成パターン等）と同様に「AIにランダムに選ばせると
  統計的な偏りが出やすい」問題を抱えていたため、コード側抽選に統一した。
- バズ構文には「○○したいなら」「○○なんてなくていいですよ。」のように、○○の部分を
  文脈に応じた単語に置き換えて使うタイプの構文も登録できる。`buzzwordUsageInstruction_(buzzword)`
  （`ClaudeService.gs`の共通ヘルパー、3プロンプトで共用）が抽選結果に応じて指示文を出し分ける。
  - バズ構文に「○○」が含まれる場合：「○○」の部分だけ文脈に合わせた適切な言葉に置き換え、
    それ以外の文言はそのまま（言い換えずに）使うよう指示する。
  - 含まない場合：これまで通り、文言をそのまま（言い換えずに）使うよう指示する。
  - この使い分けが無いと、プレースホルダー入りの構文でもAIが「○○」の部分をそのまま
    出力してしまう恐れがあるため。
- 抽選結果は各タイプの「抽選」ログに`バズ構文=◯◯`として記録される。
- **シートが空の場合**：`BuzzwordService.pickRandom()`はエラーを投げる（バズ構文は各プロンプトで
  必須要素として扱っているため、無言でバズ構文なしにフォールバックすると投稿の質が気づかれない
  まま下がってしまうことを避けるため）。`generateFixedCountBatch_`等の1件ごとのtry/catchにより、
  その回の生成のみ失敗ログに記録されてスキップされ、バッチ全体やタロット等の他タイプには影響しない。

## 情弱ポスト（拡散狙いのフックポスト）について

- `ClaudeService.generateJoujakuCaption()`で本文を1件生成する（引数なし）。画像・リプライは無く、
  本文のみのテキスト投稿（`ThreadsService.publishPost`の画像0枚パス＝TEXTコンテナ）を想定している。
- 元のプロンプトは5パターンを一度に出力する仕様だったが、自動化のため1パターンのみ出力させる。
  フックの種類・メッセージの方向性・参考パターンは、**AIに選ばせるのではなく`buildJoujakuPrompt_`内で
  `Utils.pickRandom`によりコード側で先に抽選し、選んだ結果だけをプロンプトに明記する**方式にしている
  （独立したAPI呼び出しを繰り返すとAI側の選択には統計的な偏りが出やすく、同じ組み合わせに偏っていた
  ため）。候補は`JOUJAKU_HOOK_TYPES_`（5種）・`JOUJAKU_MESSAGE_DIRECTIONS_`（8種）・
  `JOUJAKU_REFERENCE_PATTERNS_`（①〜⑤）としてコード内に定数化してある。フック内部のさらに細かい
  ランダム要素（数秘術系での具体的な数字選択など）は、これまで通りAI側の判断に委ねている。
- 文字数タイプ（短め=100〜150文字程度／長め=300〜500文字程度）も、構成パターン等とは独立に
  `POST_LENGTH_TYPES_`（情弱・HSPあるあるポスト共通の定数）から`Utils.pickRandom`で抽選し、
  「今回使う設定」に明記する。選ばれた参考パターンの構成の「型」は保ちつつ、指定された文字数に
  収まるよう調整して書くよう指示している（元々あった「100〜150文字程度を目安にする」という
  固定の短め指示は廃止した）。
- 「有効期間」は実際の日付を渡さず、プロンプトの指示で「〇日〜〇日」「今日中」などのプレースホルダー
  表現のまま出力させる（実日付への書き換えは運営が投稿前チェック時に手動で行う想定）。
- 各パターン末尾に付く「（フック種類×メッセージの方向性）」のようなメモ書きは出力させない指示を
  入れているが、保険として`stripTrailingCombinationMemo_`で応答末尾のその形式のかっこ書きを機械的に除去する。
- 抽選結果は`Utils.logEvent`で実行ログシートに記録される（種別「抽選」）。分布に偏りが出ていないか、
  後から実行ログを確認できる。
- バズ構文は`BuzzwordService.pickRandom()`でコード側抽選し「今回使うバズ構文」として明記する
  （詳細は「バズ構文シートについて」を参照）。以前プロンプト内に直書きしていた固定リストは削除した。
- 「短め」を指定しても実際は長め〜中程度の分量になってしまう問題が、HSPあるあるポストと同様の
  構造的な原因（文字数目安が「意識しつつ」という弱い表現で、500文字の方が実質的な強制力を持って
  いたこと、および冒頭の書き出し・バズ構文・有効期間表現などの必須要素が積み上がっていたこと）で
  起きうると判明したため、HSPあるあるポストで行ったのと同様の対策を適用した。
  - 「短め」の場合は冒頭の伸びやすい要素（【】・数字・感情・疑問形）を全部盛り込まず1つ程度に
    絞ってよいと明記し、要素より文字数目安を優先させる。
  - 「文字数目安が目標値、500文字はThreadsの仕様上の絶対上限にすぎない」という書き方に変更し、
    「短め」時は「150文字を大きく超えない（160文字程度までを許容誤差とする）」と具体的に明記。
  - バズ構文はコード側抽選により既に1フレーズ（7〜10文字程度）に固定されており、HSPのCTA文・
    フォロー誘導文のような「短め専用の短縮版」は不要と判断し、対象外とした。

## HSPあるあるポストについて

- `ClaudeService.generateHspAlarmCaption()`で本文を1件生成する（引数なし）。画像・リプライは無く、
  本文のみのテキスト投稿（`ThreadsService.publishPost`の画像0枚パス＝TEXTコンテナ）を想定している。
- 元のプロンプトは5パターンを一度に出力する仕様だったが、自動化のため1パターンのみ出力させる。
  テーマ・構成パターンは、情弱ポストと同様に**`buildHspAlarmPrompt_`内で`Utils.pickRandom`により
  コード側で先に抽選**し、選んだ結果だけをプロンプトに明記する方式にしている。候補は
  `HSP_THEMES_`（20種）・`HSP_PATTERNS_`（A〜E）としてコード内に定数化してある。
- 文字数タイプ（短め=100〜150文字程度／長め=300〜500文字程度）も、テーマ・構成パターンとは独立に
  `POST_LENGTH_TYPES_`（情弱ポストと共通）から`Utils.pickRandom`で抽選し、「今回使う設定」に明記する。
  選ばれた構成パターンの「型」は保ちつつ、指定された文字数に収まるよう調整して書くよう指示している
  （常に上限500文字近くまで長くなりがちだった問題への対応）。
- 各パターン末尾に付く「（テーマ×構成パターン）」のようなメモ書きは出力させない指示を入れているが、
  保険として情弱ポストと共通の`stripTrailingCombinationMemo_`で応答末尾のその形式のかっこ書きを
  機械的に除去する。
- 抽選結果は`Utils.logEvent`で実行ログシートに記録される（種別「抽選」）。
- パターンC（元・動物看護師の視点）専用の「動物看護師時代のエピソード」が、他のパターン
  （A・B・D・E）でも流用されてしまう問題があったため、`buildHspAlarmPrompt_`内で3段構えの
  対策をしている。①パターンCが選ばれた場合のみ、動物看護師関連のプロフィール2行を
  「## しずくさんについて」に含める（他パターンでは見せない）。②「## 今回使う設定」に、
  パターンに応じて「動物看護師時代のエピソードを活かして書くこと」または「動物看護師の
  エピソードや『言葉を話せない子たち』のような比喩は使わないこと」を明記する。③パターンC以外の
  場合、「## 禁止事項」にも同様の禁止を明記する。
- 本文の末尾には、いいね・保存を促す**CTA文**と、フォローを促す**フォロー誘導文**を付ける。
  どちらもテーマ・構成パターンと同様に`Utils.pickRandom`でコード側であらかじめ1つ選び、
  「今回使う設定」に選んだ文言をそのまま明記したうえで、「本文の一番最後にそのまま追加する」よう
  指示する方式にしている（AIに毎回自由に文言を考えさせない）。候補は`HSP_CTA_PATTERNS_`・
  `HSP_FOLLOW_PATTERNS_`としてコード内に定数化してある。
  - CTA文は`HSP_CTA_PATTERNS_`（5種）から必ず1つ選ばれ、毎回本文末尾に付く。
  - フォロー誘導文は`HSP_FOLLOW_PATTERNS_`（本文3種＋`null`2種）から選ばれ、`null`が選ばれた
    回はフォロー誘導文を付けない（毎回付けると押しつけがましくなるため）。出現率は配列内の
    `null`の個数を増減させるだけで調整できる（現状は3/5＝60%の確率で付与、ただし「短め」の回は
    後述の通り常に付与しない）。
  - CTA文・フォロー誘導文を含めた投稿全体で500文字以内に収まるよう、「今回の文字数目安」の
    指示と合わせてAIに一括で調整させる（文字数調整はCTA文・フォロー誘導文を削るのではなく、
    本文側を削って行うよう指示している）。
  - 抽選結果（CTA文・フォロー誘導文の選択、「なし」だった場合も含む）は`Utils.logEvent`で
    実行ログシートに記録される。
- バズ構文は`BuzzwordService.pickRandom()`でコード側抽選し「今回使うバズ構文」として明記する
  （詳細は「バズ構文シートについて」を参照）。以前プロンプト内に直書きしていた固定リストは削除した。
- 「短め」（100〜150文字程度）を指定しても実際にはほとんど短くならず、大半が長め〜中程度の
  分量になる問題があったため、`buildHspAlarmPrompt_`内で3点の対策をしている。
  - **CTA文・フォロー誘導文で短め枠を圧迫させない**：`lengthType.label === '短め'`の回は、
    通常より短い`HSP_CTA_SHORT_PATTERNS_`（5〜10文字程度）からCTA文を選び、フォロー誘導文の
    抽選自体を行わず常に`null`（付けない）にする。フォロー誘導文（30〜45文字程度）だけで
    100〜150文字の枠をかなり圧迫していたための対応。
  - **「伸びやすい要素」を全部盛り込む前提を崩す**：「短め」の回は、冒頭タグ・バズ構文・安心の
    締めなどの必須要素を全部使おうとせず2つ程度に絞ってよいことを明記し、「要素を減らしてでも
    文字数目安を守ることを優先する」よう指示する（元のプロンプトは全要素を必須としており、
    要素を全部満たすだけで100〜150文字を超えてしまう構造だった）。
  - **文字数目安を主、500文字を従にする**：従来は「文字数目安を意識しつつ500文字以内に収める」
    という書き方で、AIから見て実質的な強制力が「500文字以内」の方に偏っていた。これを
    「文字数目安が必ず守るべき目標値であり、500文字はThreadsの仕様上の絶対上限にすぎず目標値
    ではない」という書き方に変更し、「短め」の回はさらに「150文字を大きく超えないこと
    （160文字程度までを許容誤差とする）」という具体的な数値を明記している。
  - これらはプロンプト側の指示強化であり、AIの追従に完全依存する対策である点に注意。
    改善が見られない場合は、生成後の本文の実測文字数をコード側でチェックし、「短め」なのに
    大幅に超過していたら異常とみなしてエラー扱いにする（`callClaudeForText_`のmax_tokens
    打ち切り検知と同様の仕組み）安全網の追加を検討する。

## 開運ポストについて

- `ClaudeService.generateKaiunCaption(date, luckyDays)`で本文を1件生成する。
  `date`は対象日（Dateオブジェクト）、`luckyDays`は`KaiunService.listEntries()`の該当エントリの
  開運日名の配列（例：`['大安', '一粒万倍日']`）。画像・リプライは無く、本文のみの
  テキスト投稿（`ThreadsService.publishPost`の画像0枚パス＝TEXTコンテナ）を想定している。
- `GenerationService.generateKaiunBatch()`は、以前は「翌日から30日分を1日ずつ確認し、開運日
  カレンダーに該当データが無い日はスキップする」設計だったが、運用が「開運日カレンダーシートには
  投稿したい開運日だけを厳選して貼り付ける（該当日以外の空白の日付は存在しない）」形に固まったため、
  日付を総なめする処理を廃止した。現在は`KaiunService.listEntries()`でカレンダーシートの行を
  上から順に取得し、開運ポストシートにまだ存在しない日付だけを`KAIUN_BATCH_MAX_`（31）件まで
  処理する。集計ログも「対象◯日分走査、スキップ◯件」のような文言をやめ、
  「開運ポストを◯件生成」というシンプルな形にした。
- 元のプロンプトは「日付範囲を受け取り、ウェブ検索で開運日を調べたうえで複数日分の投稿をまとめて作る」
  仕様だったが、開運日の判定は`KaiunService`側で既に済んでいるため、`buildKaiunPrompt_`内で
  ウェブ検索の指示（STEP1）を削除し、`date`・`luckyDays`を入力データとしてそのまま渡す形に調整した。
  マニアックな開運日（大明日・母倉日・天恩日・神吉日・鬼宿日・天一天上・月徳日・己巳の日）の定義は、
  本文中で意味を一言添える際の参考として引き続きプロンプトに含めている。
- 「対象日の選び方」「出力の順番（前半/後半に分けて確認）」など、複数日をまとめて処理する前提の
  指示は削除し、1回の呼び出しにつき1件の投稿本文のみを出力させる。
- 参考ポストは、本体投稿とリプライへの分割（「↓」区切り）を前提とした⑥⑦⑨を除外し、
  単独の投稿として完結する①②③④⑤⑧のみを使用する（この投稿タイプにはリプライを付けないため）。
- 日付の表示形式（例：「7月6日（日）」）は`Utils.formatJapaneseDate(date)`で組み立てる。
- 文字数タイプ（短め=100〜150文字程度／長め=300〜500文字程度）を、情弱・HSPあるあるポストと同様に
  `POST_LENGTH_TYPES_`から`buildKaiunPrompt_`内で独立抽選し、「## 入力データ」に「今回の文字数目安」
  として明記する。抽選結果は`Utils.logEvent`で記録される。今回はHSPあるあるポストのような
  「短め」強化対策（要素の間引き等）までは適用しておらず、基本の仕組み導入のみ。
- バズ構文は`BuzzwordService.pickRandom()`でコード側抽選し「今回使うバズ構文」として明記する
  （詳細は「バズ構文シートについて」を参照）。以前プロンプト内に直書きしていた固定リストは削除した。

## Claude API呼び出しのmax_tokens・打ち切り検知について

- `generateJoujakuCaption`/`generateHspAlarmCaption`/`generateKaiunCaption`はいずれも最大500文字の
  投稿本文を生成する想定だが、日本語はトークン数と文字数の比率が英語より不利になりやすく、
  以前の`max_tokens=800`では長め（300〜500文字程度）の投稿やHSPあるあるポストの末尾CTA文・
  フォロー誘導文（本文とは別に付与される）を含めると出力が足りなくなり、文の途中で
  打ち切られる（`stop_reason: "max_tokens"`）事象が発生していた。対策として、
  `generateJoujakuCaption`/`generateHspAlarmCaption`は`1500`、`generateKaiunCaption`は`1200`に
  引き上げている。
- `callClaudeForText_`（Claude Messages APIを呼び出す共通処理）で、レスポンスの`stop_reason`が
  `"max_tokens"`の場合はエラーを投げるようにした。打ち切られた中途半端な文章を正常な生成結果として
  採用してしまうことを防ぐための対策で、この共通処理を経由する全ての投稿タイプ（タロット・情弱・
  HSPあるある・開運）に等しく適用される。
- `generateFixedCountBatch_`（情弱・HSPあるあるポストが使う、10件を1回のバッチ実行でまとめて
  生成する処理）は元々1件ごとにtry/catchで囲んであり、1件の生成が失敗しても
  （上記のmax_tokens打ち切りエラーを含め）ループ全体は止まらず、残りの件数の生成を継続する。
  失敗した件は`Utils.logEvent`に個別に記録され、実行ログシートで確認できる。

## Claude APIの一時的なエラー（529等）へのリトライについて

- `generateKaiunBatch`を20件実行して5件が`Claude APIエラー(529): {"type":"error","error":
  {"type":"overloaded_error",...}}`で失敗する事象が発生した。これはAnthropic側のサーバー混雑に
  よる一時的なエラーだが、原因を調べたところ`callClaudeForText_`の`Utils.withRetry`は
  `UrlFetchApp.fetch(...)`の呼び出しだけを包んでおり、`muteHttpExceptions: true`のため
  HTTPエラーステータス自体では例外が発生しない（ステータスコードのチェックはリトライ範囲の外側で
  行っていた）ため、529のようなHTTPステータスレベルのエラーは実質リトライされていなかった。
- 対策として、fetchの実行〜ステータスコードのチェックまでを1つのリトライループ
  （`fetchClaudeWithRetry_`）にまとめた。
  - リトライ対象は`CLAUDE_RETRYABLE_STATUS_CODES_`（429・500・502・503・504・529）と、
    fetch自体が投げるネットワーク例外。2秒起点の指数バックオフ（2秒→4秒→8秒）で最大3回
    （`CLAUDE_MAX_RETRIES_`）リトライする。
  - 400・401のような恒久的なクライアントエラーはリトライ対象外とし、即座に呼び出し元へ返す
    （リトライしても直らないエラーで無駄に待たせないため）。
  - `callClaudeForText_`従来の`Utils.withRetry`呼び出しはこの専用ループに置き換えた。
    汎用の`Utils.withRetry`自体（ThreadsService・Utils.logEventが使う「例外なら無条件リトライ」
    というシンプルな契約）は変更していない。

## Utils.logEventの信頼性について

- `generateFixedCountBatch_`で「実行時間はタイムアウトに達しておらず、集計ログには
  `9/10件生成`と正しく記録されているのに、対応する『失敗』ログが1件も見当たらない」という
  事象が発生したことがある。原因は`Utils.logEvent`自身の`sheet.appendRow(...)`呼び出しが
  何らかの理由で失敗し、その失敗が`catch (e) { console.error(...) }`でconsole.errorにのみ
  記録され、実行ログシートには何も残らない、という「ログ書き込み自体の失敗が握りつぶされる」
  経路があったため。（なお、`Utils.logEvent`はGASの組み込み`Sheet.appendRow()`を使っており、
  これは「最終行を読んでから書き込む」という2ステップではなく、ドキュメントで明示的に
  atomicと保証されている呼び出しのため、`SheetService.appendRow`で以前あったような
  `getLastRow()`と書き込みのタイミングずれによる行の競合・上書きは基本的に起こらない。
  問題はそこではなく、`sheet.appendRow(...)`呼び出し自体が何らかの理由で例外を投げた
  ケースが握りつぶされていたこと）。
- 考えられる失敗要因として、(a) `callClaudeForText_`のエラーメッセージにAPIの生レスポンス
  （`body`）をそのまま埋め込んでいたため、異常に長いレスポンスだとログの1セルが
  スプレッドシートの1セルあたりの文字数上限（5万文字）に近づき書き込みに失敗する可能性、
  (b) スプレッドシートサービス側の一時的な接続エラー（ユーザーが同時にシートを開いて
  操作している場合などに起こりうる）、の2つを想定し、両方に対策した。
  - `Utils.logEvent`は書き込む`detail`を2000文字に切り詰めるようにした（セルの文字数上限を
    大きく下回る範囲に収め、異常に長い内容が原因で書き込み自体が失敗することを防ぐ）。
  - `Utils.logEvent`は`sheet.appendRow(...)`を`Utils.withRetry`で2回まで短い間隔（300ms基点の
    指数バックオフ）でリトライしてから諦めるようにした（一時的な接続エラーを吸収する）。
  - `callClaudeForText_`がエラーメッセージにAPIの生レスポンスを埋め込む箇所は、
    `truncateForError_`で500文字に切り詰めてから埋め込むようにした（ログの可読性向上と、
    上記(a)の要因そのものを減らす目的を兼ねる）。
  - それでも`Utils.logEvent`自体が失敗した場合は、これまで通り`console.error`にのみ記録し、
    例外は呼び出し元に伝播させない（ログ書き込みの失敗によって本処理が止まることを防ぐため）。
    そのため、万一今後も同様の事象が起きた場合は、該当実行のApps Scriptエディタの
    「実行数」パネルから該当実行を開き、`console.error`の出力（「ログ書き込みに失敗しました:」
    という行）を確認することで、実際にどのようなエラーで失敗していたかを特定できる。

## 画像URLについて（設計上の注意）

当初は「Apps ScriptのWebアプリ(doGet)で許可フォルダのファイルIDのみ受け付ける画像プロキシ」を
実装していましたが、**Google Apps ScriptのWebアプリはTextOutput/HtmlOutputしか返却できず、
画像のようなバイナリを直接配信することができない**ことが実機検証で判明したため（`doGet`から
Blobを直接returnすると「返された値はサポートされている戻り値の型ではありませんでした」という
エラーになる）、この方式は廃止しました。

代わりに、`DriveService.getPublicImageUrl`でDriveファイルIDから
`https://lh3.googleusercontent.com/d/<ファイルID>` 形式の直リンクを組み立てて、
Threads APIの`image_url`にそのまま渡す方式にしています。「許可フォルダ内の画像のみ使う」という
制限は、取得時点でのゲートではなく、**TarotServiceが画像を許可フォルダ内でしか検索しないこと**、
および**PostingServiceが投稿直前に`DriveService.assertImagesAllowed`で再検証すること**
（承認後にシートが編集された場合の保険）の組み合わせで実現しています。

対象ファイルはDrive上で「リンクを知っている人」に共有しておく必要があります。

## 注意事項

- Threads APIのエンドポイント・パラメータ仕様は変更される可能性があるため、実装後に
  実際のレスポンスを確認しながら調整してください（特にリプライ投稿時の`reply_to_id`パラメータ）。
- 数秘術ポストは自動生成を行わない方針のため、`ClaudeService`にAI生成関数はありません。
  投稿本文はテーマ・グループを参考に運営が直接シートへ入力します。
- `SheetService.appendRow`は、直後に`SpreadsheetApp.flush()`を呼んで書き込みを確定させている。
  スプレッドシートへの書き込みはパフォーマンスのため内部的にバッチ化されることがあり、flushせずに
  `appendRow`をループで連続実行すると、直前の書き込みが反映される前に次の`getLastRow()`が呼ばれて
  同じ行番号を計算してしまい、後の書き込みが前の行を上書きしてしまうことがある（例外は発生せず、
  `generateJoujakuBatch`等で「10件生成したはずが9件しか追加されていない」という形で実際に発生した）。
